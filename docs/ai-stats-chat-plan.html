AI stats chat implementation plan

A draft for adding an authenticated, streaming assistant to the endurance dashboard. The assistant will answer questions from the athlete's own stored metrics, with the backend owning data access and the model credentials.

Draft for review No feature code changed main synchronized with origin/main Existing local work preserved in stash

What I found

Application shape

  • The frontend is React 19 with Vite, TanStack Router, and TanStack Query.
  • The backend is Hono with a typed RPC client and an authenticated route middleware.
  • The dashboard already loads daily CTL, ATL, TSB, training load, and activity counts.
  • The database also stores Strava activity summaries, computed activity metrics, athlete anchors, zones, and data-quality reports.

UI pieces already present

The shared UI package already has the current shadcn pieces needed for this chat: Message, Bubble, MessageScroller, Attachment, InputGroup, Textarea, Empty, Spinner, Button, and Card.

We should use those existing components. We should not regenerate or duplicate them unless implementation exposes a real version mismatch.

Proposed first release

Add an "Ask about your training" chat card to the authenticated dashboard below the existing metric charts. It will work on desktop and mobile, stream assistant text into the transcript, and retain the conversation in memory for the current page session.

  • Users can ask about trends, load, fatigue, freshness, recent activities, sport mix, and metric quality.
  • The assistant can request bounded, read-only training summaries from the backend instead of receiving the whole database or raw stream arrays.
  • Answers will state the date range and missing-data caveats when those affect the result.
  • The first release will not change training data, trigger Strava syncs, upload files, or give medical diagnoses.

Architecture

Dashboard chat UI → shared tool contract → SSE over existing authenticated backend URL → Hono chat route → backend tool implementation → Postgres metrics

Shared tool contract

Create a small @repo/ai package for the definitions that both applications need. This package is the seam between the frontend's typed chat UI and the backend's executable tool.

  • Export the tool name, description, input schema, output schema, and inferred input/output types.
  • Keep the package isomorphic. It may depend on @tanstack/ai and zod, but it must not import React, the UI package, Hono, Drizzle, environment variables, or provider SDKs.
  • On the backend, call trainingStatsToolDefinition.server(...) and put the database queries and authenticated user scoping in that implementation.
  • On the frontend, import the plain definition for chatOptions.tools and typed tool-part rendering. The browser receives no database implementation or provider secret.
  • If the tool becomes a group of tools, keep their definitions in this package and keep each executable implementation in the backend package.

This gives both callers one small interface while keeping the deeper database implementation local to the backend. It also lets tests validate the same schemas that the model and UI use.

Frontend chat composition

  1. Add @tanstack/ai-react and configure the current @tanstack/ai-react/ui API with createChatHook. The new API is typed and expects the app to provide the visible components.
  2. Import the shared tool definition from @repo/ai into the chat options. Register a tool-part component or a fallback so tool calls never appear as raw JSON.
  3. Define one module-scope chat configuration using fetchServerSentEvents against the backend chat endpoint. Keep browser credentials enabled so the existing Better Auth session cookie is sent.
  4. Register the visible pieces required by the UI factory: a dashboard layout, message row, text part, fallback part, and input.
  5. Build the layout from the existing shadcn pieces. Use Card for the assistant panel, MessageScrollerProvider and MessageScroller for streaming scroll behavior, Message and Bubble for rows, and InputGroup with InputGroupTextarea for the composer.
  6. Use Empty for the first-use state with a few concrete prompt suggestions, and Spinner plus a stop control while a response streams.
  7. Anchor user turns in the message scroller, mark the content busy while streaming, and preserve the reader's position when they scroll up.
  8. Render assistant text as escaped plain text in the first release. Add markdown only if the answer format needs it after the initial UI is working.

Backend chat route

  1. Add a protected POST /api/chat route to the existing Hono route tree.
  2. Parse the TanStack AI request payload and return a 400 response for malformed messages. Return 401 through the existing authentication middleware.
  3. Call chat() and return toServerSentEventsResponse(). SSE matches the documented default connection adapter and works with the existing browser-to-backend setup.
  4. Import the shared definition from @repo/ai, bind its .server() implementation in the backend, and pass only that executable tool to chat().
  5. Keep the model adapter and API key in the backend package. Add provider settings to the backend varlock schema, not the frontend schema.
  6. Set a bounded agent loop and request limits. A stats assistant should not be allowed to loop indefinitely or accept unbounded date ranges.

Stats access for the model

Use a server-side, read-only tool rather than placing a large snapshot in the prompt on every turn. Its input and output schemas live in @repo/ai. The backend implementation receives only validated filters such as date range, sport family, and an optional activity identifier. The authenticated user ID comes from the request context and is never accepted from the model or browser.

The initial tool can return a compact summary containing:

  • daily training load, CTL, ATL, TSB, activity count, and derived period summaries;
  • activity-level metrics such as sport family, duration, load, HR, pace or power values, and data-quality flags;
  • athlete anchors and zones needed to explain the calculations, with their source marked as manual or estimated;
  • coverage and sync state so the assistant can say when streams or metrics are incomplete.

Do not return raw GPS coordinates, full high-frequency stream arrays, Strava tokens, email addresses, database IDs, or another user's data. Keep aggregation and unit conversion in TypeScript so the model explains numbers that the backend already computed.

Conversation rules

  • Answer from the supplied training data. If the data does not support a conclusion, say so.
  • Distinguish measured values from estimates and explain the relevant metric in plain language.
  • Include the period used for comparisons, such as "the last 28 complete days".
  • Never invent activities, trends, causes, or exact values.
  • Use a short health and training-safety boundary for questions that cross into diagnosis or treatment.
  • Keep the first release read-only. No tool may edit profile values, zones, activities, or sync state.

Validation plan

Run formatting, lint, type checking, and the existing backend tests.
2
Exercise the route with an authenticated user, an unauthenticated user, invalid payloads, empty metrics, and a partial stream dataset.
3
Manually verify first-use, suggested prompts, streamed output, stop, retry after failure, scroll-up behavior, mobile layout, and sign-out behavior.
4
Check that provider secrets never appear in the Vite bundle or client request payload, and that two users cannot read each other's stats.

Review decisions

  1. Shared package: use a new @repo/ai package for definitions and schemas. The backend owns the .server() implementation and database queries. The frontend imports only the plain definitions needed by the typed chat UI.
  2. Provider and model: the implementation needs a provider choice. The concrete draft assumes a server-side OpenAI text adapter with the model selected by an environment variable. OpenRouter or another OpenAI-compatible provider can be substituted without changing the UI or shared tool contract.
  3. Persistence: the first release assumes session-only chat history. Persisted threads would require a conversation schema, retention rules, and a history API.
  4. Attachments: the shared Attachment component is already present, but file upload is outside the stats question scope. It should stay out of the first implementation unless you want users to attach training plans or exports.
  5. Placement: this plan puts the assistant below the charts on the existing dashboard. A separate assistant route or a drawer can be added later without changing the backend contract.
